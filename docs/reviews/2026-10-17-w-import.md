# Builder W — workbook import: preview · confirm · snapshot · history · restore

Branch `cons/w-import` from `consistency/integration` fcd23b9f (= live 2c33ed0a). Local only: not pushed, not deployed.
Isolated DB `h2budget_test_w`; preview on 3442/5242 (its own DB). Synthetic workbooks only.

## 1. What the code did before this change (read from fcd23b9f, before any edit)

### Who owns the data
- Every request carries `req.userId` (the signed-in person) and `req.householdId`. Reads are by household.
- The import, the snapshot and the restore are keyed by **`user_id` = the importing person**, not the household.
- Plaid bank rows are written with `user_id` = the household owner (`plaidSync.ts`). So the owner's import takes the
  bank rows; a member's import takes only the member's own rows.

### What `POST /api/import/workbook` replaced (one transaction, `workbookImporter.ts`)
- Deleted, for that user: every transaction (bank rows `plaid:*`, workbook rows `amex`, typed rows), budget lines,
  budget months, recurring items, mapping rules (each logged "deleted"), monthly snapshots, debts, categories.
- Taken with them by the database: category decisions, splits, debt ledger events (per transaction); balance history,
  statements, ledger events, progress snapshots (per debt). Set to empty: a milestone's debt link, a recurring item's
  or a transaction's debt link, a claim's `confirmed_by_txn_id`.
- Rewritten: `settings.preferences.amexAnchor` and the Amex debt's balance (`refreshAmexAnchor`, adopt).
- Inserted from the file: debts, categories, this month's plan lines, recurring items, rules (+ prior rules kept when
  priority > 0 or not redefined), Payments rows as `source "amex"` with the batch id, Monthly Tracking snapshots.
- The batch row and the snapshot row are written inside the same transaction (V's D1). `import_batches.summary`
  was never written.
- Validation ran **inside** the transaction, after the wipe: a bad file was rolled back (nothing kept), but it was
  not checked before the first write. No preview, no dry run, no confirmation: the page uploaded on file pick.

### What the snapshot captured (`importSnapshot.ts`, before the wipe, same transaction)
- The 8 tables above by `user_id`; the cascaded children by parent id; milestone links; the Amex anchor.
  Status `available`. The response returned `snapshotId`; the page ignored it.

### What restore returned (`POST /api/import/snapshots/:id/restore`)
- 404 when the snapshot is missing or another user's; 409 "Snapshot is restored, not available" when used.
- Otherwise one transaction: delete everything the user has **now** in the 8 tables, put the snapshot rows back
  (original ids), children, links, the anchor; rule history; status → `restored`.

### What was not covered
- **Later changes were lost without a word.** Restore deleted whatever the user had now — bank rows synced after the
  import (the sync cursor is past them; a normal sync does not bring them back), edits, new categories, rules, decisions.
- Restoring an older import after a newer one silently discarded the newer one.
- The status check sat outside the transaction: two restores at once both went ahead.
- A failed restore answered 500 with the database's own message.
- Restore turned any text value shaped like a date-time into a date (by value, not by column).
- Not touched by import or restore: bank links and balances, other preferences, other members' rows. References
  that are plain ids (merchant memory, wishlist, forecast resolutions) point at wiped categories after an import.
- The page: no history, no Restore, the error toast printed `ApiError: HTTP 400 …`.

## 2. What changed (plain words)

### Server
- **The file is read and checked before anything is written** (`planWorkbook`, pure). Every problem is collected
  (sheet, row, field), the first 20 by name and "…and N more." A recurring day the database could not store (text,
  a fraction, a date cell) is now a file problem (was a 500); every day that imported before still imports.
- **Preview** `POST /api/import/workbook/preview`: the same reading and checks, then the person's data read in a
  READ ONLY transaction. Answers what the file adds (rows, first–last day, categories, rules, debts…), what it
  replaces (rows, **bank rows with their first and last day**, categories, rules, debts, plan lines, decisions…),
  rules kept, and a `confirmToken` (person + file hash + what it replaces). Writes nothing.
- **Import** `POST /api/import/workbook` checks the file first (400 with every problem), then requires `confirm`
  (428 without). Its transaction takes a per-person lock (one import or restore at a time), re-reads what it replaces and refuses (409, nothing written) when the
  token no longer matches (another file, or a bank row arrived since the preview). The response names the snapshot
  and what it replaced. At the end it stores on the batch: counts, what it replaced, and a fingerprint of the state
  it leaves (`summary.after`: one short hash per row).
- **History** `GET /api/import/history` (≤ 20): time, file, counts, what it replaced, snapshot, and `restore`:
  available · later_import · too_old · restored · none. Only the newest import still in place is "available".
- **Restore check** `GET /api/import/snapshots/:id/restore-preview` (reads only): puts back / removes / changes
  since, `ready` or `blocked` with the reason and the count.
- **Restore** takes the same per-person lock, locks the snapshot row, runs the same check inside its transaction, and refuses with nothing written:
  404 (not this person's), 409 already restored, 409 a later import still in place ("Restore that one first."),
  409 too old (no recorded state), 409 any change since (count by kind). A failure answers 500 in plain words (was
  the database's message). Dates in a snapshot are revived by column type (was by value). `restored_at` uses the
  database clock (as the import time does).
- **What counts as a change**: every row and column of what a restore would wipe, except what the app writes on
  its own when a page is opened (found by opening all 21 pages after an import on the fixture): `GET /api/debts`'s
  daily balance row and `original_balance` fill; `GET /api/avalanche/extra`'s managed "Avalanche payment" category
  and line. They describe only the import's own rows and are rebuilt for the data put back.

### Web (Settings › Data › Workbook import; lazy chunk, hooks from the `features` client)
- Upload → preview card: "Replace N transactions, including M bank rows?" · File · Adds · Replaces · Kept ·
  "H2 keeps a copy first. History can restore it." · **Replace** / Cancel. Nothing is imported before Replace.
- A file with problems: "This file can't be imported:" + every problem + "Fix the file and upload it again."
  No confirm button.
- After Replace: "Imported N rows · Restore available in History" (and the toast keeps its rule attribution and
  View link). Every cached query refreshes.
- A stale preview (409) is previewed again with "Your data changed since the preview. Check the new numbers."
- History list: "Oct 16, 7:56 PM · file.xlsx · 4 rows" + **Restore** (newest in place) or a short status
  ("Restore the newer import first" · "Restored Oct 16, 8:01 PM" · "Too old to restore" · "No copy kept").
- Restore → "Restore your data from before this import?" · Puts back · Removes · **Restore** / Cancel; or the
  server's "Blocked: N changes since this import would be lost (…)." with Close only. Then
  "Restored · N transactions back"; every cached query refreshes.

## 8. Deviations from the brief
- Later edits are **blocked, never preserved**. No row can be kept exactly: anything added after an import points
  at the import's categories, rules or debts, which the restore replaces (keeping it means rewriting it).
- What the app writes on its own when a page opens is not counted as an edit (list in §2). The nightly budget pass
  and Sync are not on read and still block.
- Restores go **newest first**: an older import is refused while a newer one is in place (409 "Restore that one
  first."). V's test that restored the first of five imports directly now restores all five, newest first — still
  back to the seed in every part.
- Snapshots taken before this change carry no recorded state: **refused as "Too old to restore"** (the endpoint
  used to replay them blindly; no screen offered it). This includes any snapshot already in production.
- V's suite changed where the flow changed: the upload helper previews then confirms; the 409 words are now
  "This import was already restored."; the claims test's hand-made snapshot gets a batch with its recorded state.
- The dry run is `POST /import/workbook/preview` (not `?dryRun=1`); the confirmation is the multipart field
  `confirm` (or `?confirm=`); missing → 428.
- Added (not listed): a per-person transaction lock for import and restore, a row lock on the snapshot, plain
  500 words for a failed restore, 404 for a malformed snapshot id (was a 500), column-typed date revival, DB clock
  for `restored_at`, and a recurring-day check (a 500 before).
- Landing JS shrank 352 bytes instead of staying byte-identical (the old hook left the entry chunk).

## 9. Doubts for the owner
- **The restore window is short by design.** Anything new after an import blocks it: a bank sync (new bank rows),
  a filing, an edit, the nightly pass (`metrics.snapshot` → `prepareBudgetMonth`: it can add system, debt and
  bill categories and plan lines), a debt Sync. It works for "I just imported the wrong file" in the same
  sitting. Keep it strict, or allow a restore that keeps later bank rows (their categories re-pointed by name —
  not exact)?
- An import still replaces **every** transaction of the importing person, bank rows included. The preview now says
  so and asks. Refuse when bank rows would be replaced, or keep asking?
- Snapshots from before this change cannot be restored from the screen ("Too old to restore").
- Data is keyed by the importing person: a member's import replaces only the member's rows; a member cannot see
  or restore the owner's imports (404).
- A bank sync landing in the milliseconds between a restore's check and its wipe is not serialized (the sync does
  not take the import lock); the check and the wipe are one transaction, the window is tiny. Not changed.
- The confirmation token is not a secret: it stops mistakes, not a deliberate client.
- "Imported N rows" counts the Payments rows; categories, rules and debts are on the preview, not on that line.
- After the Forecast page is opened, "Removes" counts the managed "Avalanche payment" category too (it is removed
  and rebuilt), so it can read one more category than the import added.
- A numeric overflow in a cell (e.g. 1e12) is still caught by the database, not the preview (V's row-510 test
  relies on it): that file previews fine and the import answers 500 "nothing was changed".
