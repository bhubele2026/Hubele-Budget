## A. Balance check

### What a manual Sync now stores (`forecast_settings.last_bank_reconciliation`)
- Type: `BankBalanceCheckRecord` (lib/db schema). Old four-field records still read.
- `prevAnchor {balance, at, field, pendingDepositIds}` — the anchor rolled forward.
- `bank {balance, at, field}` — the bank figure compared. `anchor {balance, at, field}` — the anchor in effect after the Sync.
- `predicted`, `unexplained` (bank − H2), `status` ties / drift / not_checked, `reason`.
- Not-checked outcomes are stored with a reason instead of nothing: `anchor_too_old` (bank figure kept), `balance_unavailable` (call failed or no balance; the anchor stands).
- `lastDrift`: the last earlier drift, carried forward, so a re-anchoring Sync no longer loses it.
- `pendingDeposits`, `excluded`, `added` (ids + amount, max 200 ids), `fieldChanged`.
- Webhook / cron / non-owning-item Syncs still store nothing (unchanged).

### Where
- `artifacts/api-server/src/lib/bankBalanceCheck.ts` (new): `checkBankBalanceOnSync`, `readBankCheckLedger`, `readBankBalanceCheck`.
- `lib/avalanche-core/src/bankCheck.ts` (new, pure): `bankCheckLedger` (the comparison's rules), `bankBalanceCheckOf` (the review's answer).
- `plaidSync.ts`: the inline block is replaced by one call; it also keeps both Plaid fields and the anchor's write instant. The self-heal backfill, log lines and `balanceDrift` shape are unchanged.

### Comparison rules (reconcile only — never the curve, never the spine)
- Base: `classifyCashRows` from the previous anchor over `ledgerActualRowsWhere` rows, Plaid rows only (PR4e, reused unchanged).
- Rule 1 — pending deposits: with an `available` figure, an unpaired pending deposit is left out (`available` does not hold it). This was the false drift.
- Rule 2 — the anchor's side: a deposit pending when an `available` anchor was read (ids recorded by that read) that has since posted adds its amount (the cash rule holds every row dated before the anchor's day).
- Rule 3 — the check's own days: a charge already on the ledger at the check, or the posted row replacing a pending charge dated ≤ the check day, counts even if posting re-dated it later. Keeps a later recompute honest.
- Like with like: the bank figure is taken in the previous anchor's field when Plaid gives it; `fieldChanged` is recorded when the anchor's field changes.
- Late rows are judged on the database clock (`created_at` is stamped by it).

### Review (`GET /banking/review` → `balanceCheck`)
- `status`: matches · off_by · resolved_since · not_checked.
- `reason`: never · not_forecast_account · anchor_too_old · balance_unavailable.
- `stale` + `staleReason`: anchor_changed > rows_since > age (> 7 days). A not-checked outcome is stale by age only.
- `checkedAt`, `bank {balance, at, field}`, `h2 {balance}`, `difference` (|bank − H2|), `direction` bank_higher / bank_lower, `lastDrift`.
- `resolved_since`: recomputed from the stored previous anchor, same days, rows as they stand — one query, no Plaid call (asserted).
- `balanceTie`, `reviewInbox` and `freshness` are unchanged and stay separate.

## B. Fair "usual"
- `samePointInPeriod` (core `householdTime.ts`): weeks — same weekday; months — same day of month, capped (Oct 31 → Sep 30, Mar 31 → Feb 28/29, the 1st → the 1st).
- `GET /money/period-breakdown`, current period: per category `usual` (to date), `usualFullPeriod`, `aboveUsual` (vs to-date usual); top level `usualBasis` same_days / full_period and `usualThrough`.
- Past periods: unchanged (full vs full, `usualBasis` full_period, `usualThrough` null).
- `GET /money/ways-back`: `usualWeek` is now to today's weekday; new `usualFullWeek`, `usualBasis`, `usualThrough`.
- known / unresolved / excludedPayments / provisional (F2) untouched; categories' amounts untouched.

## Deviations / doubts
- Kept `balanceTie` beside `balanceCheck` so today's screen keeps working; F4 can switch and the lead can drop it later.
- `off_by` shows the difference found at the check; the recompute only decides `resolved_since` and `rows_since`.
- Added `lastDrift` to the review answer (not in the brief's shape) so a re-anchored drift stays visible.
- Rules 2 and 3 go beyond the brief; same false-drift family, reconcile-only, tested.
- At the check, a Plaid charge dated after today that is already on the ledger now counts (it is in `available`); before it did not. Edge only.
- `current` is not fully modelled (it excludes pending charges too, and the cash rule assumes `available`); only the field choice and `fieldChanged` are handled.
- An `anchor_too_old` check lists no pending deposits, so the next check cannot apply rule 2 to that anchor.
- No previous anchor (pointer but no balance): still nothing stored → review says "never".
- A future-dated anchor (clock skew) is stored as `anchor_too_old`.
- `checkedAt` is now the database clock just before the ledger read (was the app clock at write time).
- Ways back's "usually $X" on screen now shows the to-date figure; F4 should label it ("usual by Wed").
- Not verified on real data (no production access).
