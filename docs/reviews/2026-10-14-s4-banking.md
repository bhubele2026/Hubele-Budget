# S4: "What wasn't in the plan?" — the banking review API

Branch `fix/s4-banking`, from `fix/nav-review` (705f04c4).

- **Implemented:** all six items of the brief.
- **Tested:** new unit + integration tests; full API suite; web suite; build + entry graph; codegen drift.
- **Deployed:** no. **Enabled:** nothing (no AI, SMS, Plaid call or setting changed).

## The owner's ask
- "I want to review banking and immediately see what wasn't in the plan."
- An unmatched payment is not discretionary spending. An uncategorized row is not unplanned.
- A UN flag is not a plan comparison. Account totals stay that account's.

## What changed

### 1. Shared rules → avalanche-core (no figure moves)
- `reviewStatus.ts`: `bankLineStatusOf` (moved from the web register, `forecastMatch.ts`).
- `resolutionResolvesRow` (moved from `computeReviewCount`).
- Web `forecastMatch.ts` and `reviewCount.ts` now call them. Same answers.
- `planMatch.ts`: `pairDifference`, `pairDayDelta`, `withinStrictTolerance` — the matcher's own arithmetic.
- The matcher now calls `pairDifference` for `difference` (same formula). `pairDayDelta` pinned equal by test.
- `bankReview.ts` (new, pure): `placeBankReviewRow`, `summarizeBankReview`, `bankReviewKindOf`.

### 2. `ForecastLedger.planOccurrences[]` + `planComparison`
- Recorded at every exit of the plans loop. The fate the loop already decided, never re-decided.
- Fates: matched · partial · skipped · missed · paid_on_evidence · suggested · on_curve · overdue_outside · income_not_arrived · outside_window · not_due.
- Each: key, label, due date, planned amount (hook = its payoff), txn id + amount, remainder, evidence, `onCurve`, hook cadence.
- `planComparison {rowsFromISO: today−59, plansFromISO: first of last month}`.
- Not in `computeCashSignal` output. Golden test unchanged and green.
- Edit stays inside the plans loop (+ type and return). No change near hook sizing.

### 3. `readLedgerTotals(scope, filter, register?)`
- The totals SQL, moved out of `readLedgerPage`. The page calls it. Ledger output unchanged.
- Adds three sums the page does not show: `pendingNet`, `notCounted.superseded`, `notCounted.other`.
- `ledgerCtes` overrides now carry the register's reason (`balance_reason`). Amounts unchanged.
- `readLedgerAnchor` / `resolveLedgerScope` take an optional `signal` (one ledger per request).

### 4. `GET /api/banking/review`
- `?account&from&to[&rowsPerBucket≤50]`, page one bucket: `&bucket&kind&cursor&limit≤100`.
- Tag `banking, features` → hook in `@workspace/api-client-react/features` (off the landing chunk).
- Blocks: account · period · balance · freshness · cashFlow · planComparison · planned · notInPlan · asPlanned · reconciliation · reviewInbox · balanceTie · household · page.
- One cash-signal read per request (the spine's call, horizon 90). Register anchor, plan comparison and household all use it.

### 5. The partition (first rule wins)
1. Confirmed (matched/partial) → amountDifference (partial, or off > max($1, 1%)) · timingDifference (> 3 days) · asPlanned.
2. ignored_unforecasted / unplanned → confirmedUnplanned.
3. needs_review* → uncertain (needs_review).
4. Ledger evidence → same split, `evidence: "automatic"`.
5. Tier-3 or ambiguous pair → uncertain (suggested_match).
6. Before today−59, after today, or not the forecast account → uncertain (not_compared).
7. Else unmatched, by kind (`classifyMovement` coverage → spending · card_payment · debt_payment · transfer · income · refund · other).
- Row set: the register's counted rows in range. Replaced pending rows out (counted in `supersededExcluded`).
- A row's answer: its own; with none, its replaced pending row's (the register's own pairing).
- "Not this" is read out at SQL. UN flag and category are shown on the row only.

### 6. Balance tie storage
- `0190_last_bank_reconciliation.sql`: nullable `forecast_settings.last_bank_reconciliation jsonb`.
- Drizzle column added; `schemaMigrations` test replays it; README range 0190s = NAV-S4.
- `plaidSync` writes `{checkedAt, accountId, unexplained, status}` right after the final recon. Best effort.
- Only on a manual Sync with a reconcilable anchor (as before). `balanceDrift` unchanged.
- The review only reads it. Wrong account or none → `not_checked`.

## Deviations from the brief (code wins, intent kept)
- **Rule 4 also takes the ledger's own "paid" rows** (`planOccurrences` fate `paid_on_evidence`).
  - Covers `overdueAssumedPaid`, a paycheck the ledger counts as arrived, and a hook's payoff paid by an Amex payment.
  - Without it a paycheck would read "paid" in `planned[]` and "uncertain" in the rows.
- **Rule 6 also covers rows after today.** The matcher reads rows through today only.
- **Carry-over uses the register's pending pair** (`replacedPendingId`), not `confirmedMatchIds`' pairing.
  - Same pairing that excludes the pending row, so no row is counted twice.
- **A confirmed row whose plan is older than the ledger's window** → asPlanned with no plan detail (`asPlanned.withoutPlanDetail`), or amountDifference (partial).
- **Extra fields:** `cashFlow.otherExcluded`, `planComparison.through`, `asPlanned.pendingNet/withoutPlanDetail`, `reconciliation.rowsPlaced/rowsUnexplained`, `account.isForecastAccount/lastSyncedAt`, row `description/manual/evidence`, `planned[].onCurve/remainder/hook`.
- **Household block** uses the position's `spentWeekDiscretionary` / `weekCap` / `remainingWeek` (same week, same scope). Not the spine's `spentWeek` (a different total).
- **Fixtures:** extended `amexCheckingScenario` (review at every step). Per-rule cases in a new `_fixtures/bankingReviewScenario.ts` (householdScenario has no plan pairs).

## Open / doubtful
- `reviewInbox.unresolvedInRange` differs from the badge when an answer sits on a replaced pending row (fixture: 15 vs 16). S6 owns the badge fix.
- Kind "transfer" includes bank-noise wording (e.g. "AUTOPAY", "ACH PMT") — the spending rule's own answer, shown as is.
- A confirmed row older than the first of last month has no plan detail (the ledger does not expand that far).
- The tie is only as fresh as the last manual Sync; `checkedAt` is returned so the page can say when.
- A row written between the register read and the row read could make `unexplained` non-zero for that one response (no transaction spans the reads).
- Rule 4 counts a paycheck the ledger takes as arrived (a nameless, non-ambiguous deposit) as planned. The brief's narrower rule would call it uncertain. Lead's call.
- The row's kind reads its filing through `loadMoneyContext`'s pending pairs (as every spending report does); the answer carry-over uses the register's pairs. Same rule (`canSupersede`), different read windows; they could disagree on a rare pair.
- Every request also builds the household position (one more read of the week). Cheap next to the ledger, but not free.
