## What it does

| Route | What you get |
|---|---|
| `/activity` | Ledger (cursor, 50 a page, Load more) grouped by household day; search (250 ms debounce, server `ILIKE`); range chips (this week / this month / last month / custom); account filter; "Needs filing" toggle; the category chip files a charge in two taps; row menu (Split, Mark reimbursable, details); "Needs attention" findings; "Handled by H2" trail |
| `/activity/review` | The review queue, oldest first, 20 at a time: proposed category (provisional chip), one line why, flags as words, Accept / Change / Skip; keys j k a s c |
| `/activity/rules` | Learned rules: category and scope change inline, turn off, delete (asks first), explicit "Apply to past charges"; link to the frozen hand-written rules |
| `/design/activity[/review|/rules]` | Public sample page, query cache seeded, no network, labelled "Sample" |

## S1 carry-overs

- **Dock never covers the last control:** `Shell` bottom padding is now `calc(6rem + env(safe-area-inset-bottom))` on a phone (the dock is about 64 px plus the inset).
- **"Needs filing" is a count of charges** ("3 charges need filing", link "File them" to `/activity?unfiled=1`). Source: `GET /transactions/ledger?uncategorized=true&from=weekStart&to=weekEnd&limit=1`, its `matchingCount`; asked for only when the position says something needs filing. No dollars.

## Data sources (all generated hooks, explicit cache options)

Ledger infinite (2 min), categories and Plaid items (30 min), review queue and agent trail/findings (1 min), learned rules (5 min). The trail's key and options are shared by Today and Activity (`data/trailQuery.ts`); the review key by the badge and the Review screen. Ledger requests are always `from`/`to` bounded with `limit=50`; every filter is a query parameter. After a write the review, rules and trail lists are invalidated (`invalidateActivity`); ledger and spine invalidate through the existing mutation cache.

## API gaps found (frontend works around each; each wants a small API follow-up)

1. **`PATCH /transactions/:id` does not return the decision id** (nor the learned rule id), although `recordHandFiling` computes `decisionId`. Undo therefore cannot call `POST /category-decisions/:id/undo` today. The code uses `res.decisionId` when it appears and otherwise puts the previous category back (PATCH) or clears it (`uncategorize-by-ids` with a `fromCategoryId` guard). Side effect of the fallback: the put-back is itself a hand filing, so merchant memory follows the latest choice. **Ask:** return `decisionId` (and `learnedRuleId`) from the PATCH.
2. **"Apply to N similar"** finds the rule in `GET /learned-rules` by the row's `merchantSignature` plus the category just chosen (same signature function as the server), then POSTs `apply-retroactively`. Works; a `learnedRuleId` in the PATCH response would remove the extra read.
3. **Ledger rows carry no split count and no `categoryProvisional` in the generated types.** Provisional is read defensively from the row; "split ×N" is known for splits made this session (and `splitCount` if the API ever sends it), and the details sheet always fetches the real splits. **Ask:** `splitCount` and `categoryProvisional` on ledger rows.
4. **No "hide a charge" exists on the API**, so the row menu has no Hide. **No per-charge decision history endpoint** on this base, so "How it was filed" reads from the row's own flags (locked / provisional / matched rule).
5. **Rules page count:** there is no preview of how many past charges a rule would file, so "Apply to past charges" reports the count after it is pressed.
6. `POST /agent/actions/:id/undo` returns 501 for `set_category` until AI-1: the trail shows Undo only when `reversible && !undoneAt` and a 501 becomes the quiet toast "Undo arrives with the next update."
7. The brief's `useGetBudgetCategories` does not exist; `useListCategories` (`/budget/categories`) is used, the same key Today reads.

## Design choices to confirm

- The category "popover" is the kit's Sheet (focus trap, Escape, return focus for free; works on a phone).
- The row menu is a Sheet too, which doubles as the details view. Long-press is not wired.
- Toasts are a small kit component (`kit/Toast`), mounted only inside the Activity chunk.
- Review count in the badge adds the queue total and `spine.reviewCount` as the brief says; these are different counts on the server (queue vs unresolved Chase rows), so a household can see both.
