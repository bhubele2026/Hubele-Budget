## What changed

### 1. `POST /api/allowance-plans` (new)
- Body `{period: weekly|monthly, amount, effectiveFrom}`; strict (unknown keys → 400).
- Owner only — the PUT's rule (`actualUserId === householdOwnerId`); a member → 403.
- Weekly: a household Sunday (America/Chicago), this week's or later.
- Monthly: the 1st, this month's or later.
- Amount: dollars and cents, more than $0.
- One rule, pure: `planStartProblem` (allowancePlanWriter.ts).
- Writes through the new `createOwnerAllowancePlan` — still the only writer module.
- A pool row already starting that day is updated (`created: false`); else inserted (`created: true`).
- Response: the plan row + `created` + `inEffect`.

### 2. `PUT /api/allowance-plans/:id` stops rewriting history
- Row started before this week (month): left as it is; the edit becomes the plan from this Sunday (the 1st) on → `created: true`.
- Same edit again: updates that new row (no third row).
- Row starting this period or later: edited in place.
- A new `effectiveFrom`: must be a period start, this period or later → else 400.
- The rule lives in the writer, so an approved `weekly_limit` proposal versions too.

### 3. `GET /api/allowance-plans` adds
- `inEffect {weekly, monthly}`: the row in effect this week / this month, by the position's rule ($0 row = null).
- `prefills[] {period, amount, source, label}` — options only, nothing writes them:
  - `hook_stored` — the hook item's stored amount, label "Weekly Spend reserve" (active, non-income item only).
  - `suggested` — the existing suggested weekly cap, label "Suggested".
  - `settings` — the saved allowance amounts if > 0, label "Saved allowance".

### 4. One "no plan" rule in the forecast hook
- `loadHookPayoffs` caps each period with `weeklyCapCents` / `monthlyCapCents` — the position's and breakdown's helpers.
- Dropped: the fallback to `settings.weekly/monthly_allowance_amount`.
- Also follows from the rule: a $0 per-week override is no plan (was a $0 cap).
- No plan → the occurrence keeps the item's stored amount (unchanged rule) and says so.

### 5. The reserve is labelled
- Cash signal (and the forecast bundle that embeds it): additive `hookReserves[]`.
- Each: `{hook, recurringItemId, planKey, occurrenceDate, label, amount, basis: plan|stored_amount}`.
- Straight from the ledger's `hookPayoffs` (`fromStoredAmount`); nothing recomputed.
- Web `hookPayoffsOf` reads it. Register line under the hook row:
  - no plan: **"Weekly Spend reserve $380 · no weekly plan set"**
  - plan: unchanged, "card payoff $355.00 · plan $380"
  - paid on evidence, no plan: "paid on evidence by <row> · no weekly plan set"

## Decisions (made, not asked)
- `hookReserves` is per occurrence (adds `planKey`, `occurrenceDate`): a plan can start mid-horizon, so one hook is stored one week and plan-based the next.
- POST on a start that already has a row updates it — the tap is idempotent, and a $0 row from the classic page cannot block "Use $X".
- Versioned PUT when this period already has a row: updates that row (created false), not 409.
- PUT `effectiveFrom` must now be a period start (was: any calendar date) — same rule as POST.
- `inEffect` reports plan rows only; a per-week override is not a row (position/breakdown say `source: override`).
- Fixtures use made-up amounts ($380, $340, $600 …), never the live $450 / $500.
