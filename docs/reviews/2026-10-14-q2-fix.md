# Q2 Correction workflow — preview, apply, audit, undo (branch prem/q2-fix, from prem/integration 8bfc7127)

Server + spec/codegen only (Q5 builds the screens). Synthetic fixtures only. Nothing in production touched.

## What changed
### 1. Direction guards (commit 1)
- `directionConflictsOf` (`categorizer/review.ts`): the queue's rule (`categoryDirectionConflict`) for many rows in 3 reads.
- Judged on the row as the write leaves it (`directionPatchOf`: a body that also sets amount / transfer / debt / reimbursable).
- Now in front of:
  - `PATCH /transactions/:id` (category picked) → 409 `ReviewRefusal` (`direction_conflict`).
  - `POST /transactions/bulk-update` → 409 `DirectionRefusal`, every conflicting id. One bad row refuses the whole call.
  - `POST /transactions/recategorize-by-pattern` → same; checked before the rule re-point, so nothing is written.
  - agent `applyProposal` set_category → 409 `code: direction_conflict`.
  - Ask's direct set_category (the person asked) → tool error `direction_conflict`. (Not in the brief; same write.)
- Exception: a pattern Undo (`lockedIds` present) restores the rows' own earlier filing and is not judged.

### 2. Undo gaps (commit 2)
- `category_decisions.flags_before / flags_after` (0210, additive, nullable): is_transfer, its person's override, weekly / monthly / unplanned.
- Written by PATCH, bulk-update, recategorize, the queue, the agent, Ask.
- Undo restores each flag the decision changed; a flag it did not change is never touched.
- Older decisions (no snapshot): category only, as before.
- `writeForecastResolution` (`lib/forecastResolutionWrite.ts`): the route's 3 neighbour deletes + insert, moved unchanged.
  - Takes an executor; returns the row and EVERY row it deleted.
  - `resolutionNeighbours` reads what it would delete (same conditions). `restoreForecastResolutions` puts rows back by id.
  - `POST /forecast/resolutions` calls it with the pool: same statements, same order.
- `setCategoryByHand` → `writeCategoryByHand(tx, …)` + `handPickPatch` (the one definition of a hand pick's columns).

### 3. Apply a proposal (commit 3)
- `POST /review/proposals/:key/apply` (owner only). Body `{ rowIds, proposalHash }`.
  - Recomputes the proposal; refuses 409 `proposal_gone` / `proposal_changed` (hash or listed ids differ).
  - income_category, transfer: category via the user-decision path (row locked, user decision with flags).
  - loan_payment: category (when the proposal names one) + mark matched per row's occurrence.
  - bill_match: mark matched.
  - Two rows on one occurrence: the row dated nearest it answers; the other is `occurrence_shared`.
  - Memory learned ONCE per fix (first listed row), sign-aware (`in:` for money in).
  - 409 `no_target_category` (a transfer proposal with no Transfer category), `direction_conflict`, `already_applied`.
  - Two taps: advisory lock per household + key; a live record with the same hash refuses the second.
- `?dryRun=1`: writes nothing. Rows before → after, answers it would replace, figures before → after.
- Audit: new table `correction_applications` (0211). Not `agent_actions`: every agent row needs an `agent_runs` run (NOT NULL).
  - Keeps: each row's 8 columns before/after, decision ids, created + deleted resolutions, reopened queue ids, memory before/after.
- `POST /review/proposals/applied/:id/undo` (owner only): the whole fix, exactly.
  - Rows, answers (deleted ones back with their ids), queue items reopened, decisions marked undone, memory restored.
  - Memory changed since: the rule it taught is switched off instead (`memory: "disabled"`).
  - Refuses 409 `changed_since` naming the rows and answers when one changed or a new answer took the key. Nothing written.
- `GET /review/proposals/applied`: last 20, newest first.

### 4. Row links
- Proposal rows: `account.externalId` (Plaid account id) + `source`. New schema `ReviewProposalAccount` (PeriodBreakdownAccount unchanged).

## How the dry run reads "after"
- `lib/correctionOverlay.ts` (pure, no writer imports — the agent's closure reaches it):
  - row patches = `handPickPatch` (the apply's own columns), resolutions added/removed, occurrences answered.
- Threaded as an explicit option (the `planOverride` pattern):
  - `loadMovementRows`, `loadConfirmedMatchRows`, `loadMoneyContext`, `loadAllowanceWindow`, `loadPositionInputs`,
    `readPeriod` / `buildPeriodBreakdown`, and the Budget month.
- Budget month: `GET /budget/months/:m` body moved into `buildBudgetMonthView` (same file), unchanged; the route calls it.
- One ledger for before and after (built once per dry run).
- Ledger pairs/suggestions naming an occurrence the fix answers are dropped (`tier2PairedAfter`, `suggestionsAfter`).

## Deviation (forecast ledger + Banking review)
- The lead said: stay out of `forecastLedger.ts` and `bankingReview.ts` (F5). Both read the DB directly.
- So the dry run cannot rebuild the ledger or re-place Banking rows. Stated per response in `limitations`:
  - `forecast_pairs_as_before` (when the fix writes answers): a row the fix frees or crowds out may pair elsewhere once written.
  - `banking_after_not_previewed`: Banking buckets come `before` only, `after: null`.
  - `listed_rows_only`: a truncated proposal applies to its 20 listed rows.
- No write-and-rollback anywhere.
- Follow-up after F5 merges (small, additive):
  - `buildForecastLedger(…, { correctionOverlay })`: filter `resolutionsStored` by `removedResolutionIds`, append the
    added answers (`addMatched` carries item + date), `patchRows` on `actualRowsAll` / `candidateRowsAll`. Unshared build.
  - `buildBankingReview(…, { overlay })`: `patchRows(rows)`, answers ± the overlay in `readRowAnswers`, overlay into
    `loadMoneyContext` / `buildMoneyPosition`, the overlay ledger.
  - Then `previewCorrection` passes both; the two limitations go.
