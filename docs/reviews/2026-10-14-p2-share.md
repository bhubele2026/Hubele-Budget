# P2 — build the forecast once and share it (branch perf/p2-share, from perf/integration 21a51339)

API + lib/db only. No spec, schema, migration or web change. No figure moves.

## What changed
- In-flight sharing: concurrent `computeCashSignalDetailed` calls with the same inputs await ONE build (`lib/ledgerShare.ts`, `lib/cashSignal.ts`).
- Narrowest shared point: `computeCashSignalDetailed`. It is the only caller of `buildForecastLedger`; `computeCashSignal` is `.signal` of it. Sharing there also shares the walk.
- Key (`cashSignalShareKey`): household, owner, `horizonDays`, `fromDate`, household today. `buildForecastLedger` reads no other option and no other clock.
- Plus a write generation: any non-GET request under /api bumps it at start and at finish (`middlewares/ledgerWriteFence.ts`, first in `routes/index.ts`). A read that starts after a write never joins a build from before it.
- Entry deleted when the build settles (success or failure). No rejection kept. No result cache.
- Kill switch: `LEDGER_SHARING=off` (read per call).
- Windowed pairing: `computeWeeklyPayoff` → `findSupersededPendingForRange(h, queryStart, queryEnd)`; `buildAmexSummary` → `(h, from, to)`; `buildBehaviorFacts` → `(h, TRACKING_START, max(end, today))`.
- Parallel reads in `buildForecastLedger`: settings, recurring, debts, hook settings, Avalanche settings, resolutions, debtMinSchedule import → one `Promise.all`. Then snapshot account, actual rows, matched rows → one `Promise.all`.
- Parallel reads in `computeWeeklyPayoff` (categories, card debts, rows, pending pairs) and in `loadHookPayoffs` (card charges ∥ open-period spend).
- Pool: `connectionTimeoutMillis: 10_000`; `watchPoolWaiting` logs waiting/total/idle when queries queue (at most every 30 s), wired in `index.ts`.

## Deviations from the brief (and why)
- Write generation added to the key. Without it, "Mark matched → refetch" could join a spine build that started before the write and show the old answer. Background jobs do not bump it (no caller waits on them).
- `behaviorFacts`: it reads two row sets (the range and the streak rows from TRACKING_START to today), not one. Both lie in `[TRACKING_START, max(end, today)]`, so the windowed read over that span is exact. Proven against the whole-history answer.
- `buildForecastLedger`: the pure resolution block (paused reviews, orphan remap, moved-bill recovery, `matchedIds`) now runs before the account/actual-rows block, so the matched rows read with them. Neither block reads the other's results.
- The candidate-rows read is still sequential (whether it runs depends on the matching plans). Left as is.
- Not done here: P3's per-request memo, indexes and the badge count.

## Left / doubts
- Local numbers, not Render: the machine is far faster than 0.5 CPU. Ratios are the signal; live needs the read-only re-measure after deploy.
- Query count per build rises by a few (the windowed read is 2 small queries vs 1 full-history join): each is ms, the join was the cost.
- Queries inside `db.transaction` are not counted by the harness (none of these GETs opens one, as far as read).
- Sharing and the write generation are per process. Fine on one Render instance; several instances would each build once.
- ×8 "spine alone" before (2,177 ms) is slower than the spine inside the 8-together run (1,814 ms): it is the first scenario of the run. Medians, one warm-up; taken as measured.
- `lib/db/dist/schema/index.d.ts` shows key-order noise after `tsc -b`; not committed.
