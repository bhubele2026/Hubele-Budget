## What changed
- **Badge count.** `GET /api/categorization/review/count` → `{ total }` from `openReviewCount` (the list's own `total`, same filters). Spec first, codegen committed.
- **Review queue, one history read.** `listReviewQueue` ran the list, then the count, then one whole-history ILIKE read per listed item, in sequence (20 for the badge on every page).
  - Now: list ∥ count, then ONE read for every item's merchant history (`rowsWithSignatures`), grouped in memory.
  - The grouped read asks SQL which signature tokens each row matched (the single read's own ILIKE); a row counts for a signature only if it matched THAT token and carries that signature. Same rows, same order as `rowsWithSignature` per item.
  - Queries per page: 2 + one per item → 3.
- **Amex in one call.** `/amex/summary` `scope.cards[]` carries `purchases { amount, count }` per card: same rows, rule and tally as the top-level `purchases` (one map beside the existing tally). Present for `all` and for one card.
- **Indexes** — `lib/db/migrations/0200_transactions_read_indexes.sql` (0200s reserved for PERF-3 in the README), mirrored in the drizzle schema by name:
  - `transactions_household_account_pending_idx` (household_id, plaid_account_id, occurred_on) WHERE pending
  - `transactions_account_occurred_idx` (plaid_account_id, occurred_on)
  - `transactions_household_source_account_idx` (household_id, source, plaid_account_id)
  - Plain `CREATE INDEX IF NOT EXISTS`: the runner wraps each file in one transaction (`BEGIN … COMMIT`, 15 s lock_timeout), so no CONCURRENTLY.
- **No debt auto-refresh.** `GET /debts` no longer calls Plaid or writes liability data. Removed the "> 1 h stale → fetch liabilities → applyLiabilityToDebt" block and `REFRESH_STALE_MS`. No background job.
  - Manual Sync already refreshes: `POST /plaid/sync` → `fetchLiabilitiesForItem` → `applyCachedLiabilitiesToPlaidDebts` (per synced item with a credit/loan account). Nothing new wired.
  - A debt's own Refresh (`POST /debts/:id/refresh`) is unchanged.
  - Stale comments that said "as GET /debts does" updated (spine.ts, plaid.ts, debtLiabilityApply.ts).

## EXPLAIN before → after
- Scratch DB, synthetic: 4 households, 6 accounts each, 3 years; target household 16,667 rows (661 pending, ~70% with a posted twin). Hand-written SQL equal to the code's reads. `VACUUM ANALYZE` before each side; 3 runs each.
- Script: scratchpad `p3/seed.sql` + `p3/queries.sql` (not committed).

| query | before | after | plan change |
|---|---:|---:|---|
| Q1 pairing join, whole ledger (`findSupersededPending`) | 157–185 ms | 150–155 ms | pending side: partial index, 661 rows (was 16,667 filtered); still a merge join |
| Q1b pairing join, windowed (`findSupersededPendingForRange`, P2) | 0.89–0.95 ms | 0.59–0.72 ms | pending side: partial index, 33 rows (was 795 filtered) |
| Q2 Amex card discovery `SELECT DISTINCT` (`amexAnchorRead.ts`) | 1.23–1.34 ms | 0.65–0.70 ms | index-only scan, 0 heap fetches (was bitmap heap scan of 8,327 rows) |
| Q3 card window, 3 cards × 1 week (`amexSummary.ts`) | 0.11–0.13 ms | 0.10 ms | planner keeps BitmapAnd; with fresh stats only (no VACUUM) it took the new index: 0.03 ms |
| Q3b 1 card × 1 month | 0.06 ms | 0.06 ms | unchanged |

- ⚠️ Q1 (whole ledger): with the new (plaid_account_id, occurred_on) index a nested loop runs in 6–8 ms (forced), but the planner prices it at 13,054 vs 3,561 for the merge join and keeps the merge join. Indexes alone do not fix that query; P2's windowed pairing does for the readers it moved. Readers still on the whole-ledger join keep its cost.

## Deviations, doubts, left undone
- **"GET must never write"**: GET /debts still upserts today's balance snapshot for each active debt and backfills a missing `originalBalance`. Neither calls Plaid or refreshes anything; removing them would move the history curve and % paid. Kept; say so if you want them gone too.
- Sync applies liabilities only to debts whose **balance** Plaid owns (`balanceSource = 'plaid'`). The old GET refresh also updated a Plaid-owned APR/minimum on a debt with a manual balance. Those now update on that debt's own Refresh only. Not widened (would change what Sync writes).
- `GET /plaid/liability-accounts` still fetches liabilities once when nothing has been fetched yet (the link picker). Not a debts read; left.
- Badge client wiring is P4. Key to use: `[...getListCategorizationReviewQueryKey(), "count"]` (= `["/api/categorization/review", "count"]`), so `review-categories.tsx` ≈74, `AutomationTab.tsx` ≈81 and `LearnedRulesPanel.tsx` ≈101 still refresh it. Tagged `categorization` only (main module, entry-safe).
- Two server callers still call `listReviewQueue(hh, 1)` just for `.total` (`index.ts` recap counter, `metricsSnapshot.ts`): now 3 cheap queries; could call `openReviewCount`. Not changed (jobs, not page loads).
- Three more indexes on `transactions` = a little more write work per Plaid sync insert. Small at this size.
